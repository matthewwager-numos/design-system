# DropdownMenu

A menu of actions or options that opens from a trigger. This is the shared foundation `<Select>` is built on — a styled trigger paired with this same menu panel.

## When to use

- A list of actions attached to a button (row actions, a "more" menu, a user menu).
- As the popover half of a custom select-like control.

## When NOT to use

- For a plain multi-choice form field — use `<Select>` once it ships; it wraps this same menu with a field-styled trigger and keyboard/typeahead behavior tuned for forms.
- For persistent navigation — use `<Navigation>`.

## Implementation

This is a compound component: `<DropdownMenu>` (root, owns open state) wraps a `<DropdownMenuTrigger>` (clones its child — pass any single interactive element) and a `<DropdownMenuContent>` (the panel, only rendered while open) containing `<DropdownMenuItem>`s.

```tsx
import { Button, DropdownMenu, DropdownMenuTrigger, DropdownMenuContent, DropdownMenuItem } from "@numosai/ui";
import { User, Settings, LogOut } from "lucide-react";
import "@numosai/ui/styles.css"; // once, at your app entry

<DropdownMenu>
  <DropdownMenuTrigger>
    <Button variant="secondary">Open menu</Button>
  </DropdownMenuTrigger>
  <DropdownMenuContent>
    <DropdownMenuItem leadingIcon={<User size={16} />}>Profile</DropdownMenuItem>
    <DropdownMenuItem leadingIcon={<Settings size={16} />}>Settings</DropdownMenuItem>
    <DropdownMenuItem leadingIcon={<LogOut size={16} />}>Log out</DropdownMenuItem>
  </DropdownMenuContent>
</DropdownMenu>
```

### Controlled open state

For cases where something else needs to open/close the menu (e.g. a parent form), skip `defaultOpen` and control it directly:

```tsx
const [open, setOpen] = useState(false);

<DropdownMenu open={open} onOpenChange={setOpen}>
  ...
</DropdownMenu>
```

### Active and disabled items

`active` renders Figma's filled "Active" state — useful for marking the currently selected option (exactly what `<Select>` will use it for). `disabled` skips both pointer and keyboard interaction.

## Sizes

Size is set once on the root — `<DropdownMenu size="sm" | "md" | "lg">` — and shared via context by every `<DropdownMenuContent>`/`<DropdownMenuPanel>` inside it, cascading down to each item. A trigger built at "md" and a `<DropdownMenuContent>` opened at "lg" can't drift out of sync this way, since there's only one place to set it:

```tsx
<DropdownMenu size="md">
  <DropdownMenuTrigger>...</DropdownMenuTrigger>
  <DropdownMenuContent>...</DropdownMenuContent>
</DropdownMenu>
```

`<DropdownMenuContent>`/`<DropdownMenuPanel>` still each accept their own `size` prop directly, overriding the root's, for the rare case that genuinely needs to — but the root is where `<Select>`/`<MultiSelect>`/`<SearchFilter>` set it, once, from their own `size` prop.

## Width

`<DropdownMenuContent matchTriggerWidth>` (default `false`) matches the panel's width to the trigger's own measured width — what `<Select>`/`<MultiSelect>` use for their options list, so it lines up with the field that opened it rather than shrinking to its content. `<DropdownMenuPanel>` defaults this to `true` instead, since a panel is almost always anchored to a full-width field (`<SearchFilter>`'s own filters panel, for instance).

## Placement

`placement="bottom" | "top"` (defaults to `"bottom"`) is a *preferred* side, not a fixed one — the panel automatically flips to the other side, and/or right-aligns instead of left-aligning, whenever the preferred combination would run it off the edge of the viewport once its real rendered size is known. A trigger pinned near a corner (a table row's kebab menu, `<Navigation>`'s `<NavUser>` account menu near the bottom of the sidebar) ends up wherever actually keeps the whole panel on-screen — `placement` just picks which side to try first.

```tsx
<DropdownMenuContent placement="top">...</DropdownMenuContent>
```

## DropdownMenuPanel: any input components

`<DropdownMenuContent>` is a `role="menu"` full of `role="menuitem"` rows — right for a list of actions or options, wrong for a form. Matches Figma's `Dropdown` `type="Filter"` variant: swap it for `<DropdownMenuPanel>` when what opens from the trigger is arbitrary fields (`<Checkbox>`, `<Slider>`, a date field, `<TextInput>`, ...) instead of a list to pick from — same `<DropdownMenu>` root, same open/close/positioning/outside-click, just a plain padded box instead of a menu, so each field keeps its own native keyboard behavior (arrow keys move a slider, not the menu's selection).

```tsx
import { Button, Checkbox, DropdownMenu, DropdownMenuTrigger, DropdownMenuPanel, Slider, TextInput } from "@numosai/ui";
import { Filter } from "lucide-react";

<DropdownMenu>
  <DropdownMenuTrigger>
    <Button variant="secondary" leadingIcon={<Filter size={16} />}>Filters</Button>
  </DropdownMenuTrigger>
  <DropdownMenuPanel>
    <TextInput label="Name contains" placeholder="e.g. invoice" />
    <Checkbox label="Only overdue" />
    <Slider label="Minimum amount" defaultValue={40} />
  </DropdownMenuPanel>
</DropdownMenu>
```

<Canvas of={DropdownMenuStories.FilterPanel} />

Unlike `<DropdownMenuContent>`, opening a `<DropdownMenuPanel>` doesn't move focus anywhere — there's no safe assumption about what (if anything) inside arbitrary children should receive it. Escape still closes it and returns focus to the trigger; there's no Arrow/Home/End handling, since those belong to whatever field has focus, not to the panel itself. `<SearchFilter>` is the real, worked example of this in practice — see its own docs page.

## Behavior

- **Closes on**: clicking outside, selecting an item (unless `closeOnSelect={false}` is passed to that `<DropdownMenuItem>`), or pressing Escape (which also returns focus to the trigger).
- **Transition**: the panel fades and scales in/out (`--duration-fast`) on open/close. It stays mounted for the duration of the close animation rather than disappearing instantly — implemented with plain CSS + a mount/visible state split, no animation library.
- **Keyboard**: Arrow Down/Up move between items (wrapping), Home/End jump to the first/last, Enter/Space activate the focused item — all native `<button>` behavior, nothing custom.
- **Viewport collision**: handled automatically (see Placement above) — the correction happens inside the panel's own hidden "just mounted" frame, so only the final, already-correct position is ever visible, no flash of the wrong placement first.

## Accessibility

- Trigger gets `aria-haspopup="menu"` and `aria-expanded` automatically via `<DropdownMenuTrigger>` — including when paired with `<DropdownMenuPanel>`, where `"menu"` isn't really accurate (there's no menu, just a panel of fields). Fixing that means changing what every `<DropdownMenuTrigger>` consumer gets, so it's a known, minor inaccuracy rather than something worked around per-consumer.
- `<DropdownMenuContent>` is a real `role="menu"` with `role="menuitem"` children in `role="none"` list items, per the WAI-ARIA menu pattern. Opening it moves focus to the first enabled item; Escape returns focus to the trigger.
- `<DropdownMenuPanel>` has no special role — its own children (real form fields) carry their own semantics. Escape still closes it and returns focus to the trigger; focus is otherwise left wherever it already was.
