# SearchFilter

A search field with a filter button that opens a panel of arbitrary fields — matches Figma's Search/Filter input exactly. Built from the same pieces as everything else: `<SearchInput>`'s own field anatomy, `<FieldLabel>` for the label, and `<DropdownMenu>` + `<DropdownMenuPanel>` (the "any input components" variant of its content — see the DropdownMenu docs) for the filter panel itself.

## When to use

- Search modeled on Gmail's own search bar: type freely, or open a structured filter builder that composes into the same field, rather than a separate "Advanced search" page.
- When the set of filterable fields is genuinely arbitrary — a date range here, a status checklist there — not a fixed schema this component could know in advance.

## When NOT to use

- A fixed set of 1-3 filters always visible — plain `<Select>`/`<Checkbox>` controls next to the search field are simpler than hiding them behind a panel.
- Free-text search with autocomplete suggestions and no structured filters at all — that's `<SearchInput>`, not this component.

## Implementation

```tsx
import { Checkbox, SearchFilter, Slider, TextInput } from "@numosai/ui";
import "@numosai/ui/styles.css"; // once, at your app entry

<SearchFilter
  label="Invoices"
  filters={
    <>
      <Checkbox label="Only overdue" />
      <Slider label="Minimum amount" defaultValue={40} />
      <TextInput label="Customer" placeholder="e.g. Acme Co." />
    </>
  }
/>
```

## `filters` is genuinely just a slot

SearchFilter doesn't know or care what's inside `filters` — any input components, in whatever layout you want (it's rendered inside `<DropdownMenuPanel>` exactly as given). It doesn't validate them, read their values, or coordinate them with the search field's own `value` for you.

## Building "standard filter notation"

The field showing something like `status:overdue amount:>40` isn't a separate display mode SearchFilter computes — it's just the field's own `value`, the same one you could type into directly. Wire each filter control's `onChange` to recompute that notation string and call `onChange`, the same value whether it came from typing or from the panel:

```tsx
const [query, setQuery] = useState("");
const [overdue, setOverdue] = useState(false);

function applyFilters(nextOverdue: boolean) {
  setQuery(nextOverdue ? "status:overdue" : "");
}

<SearchFilter
  value={query}
  onChange={setQuery}
  filters={
    <Checkbox
      label="Only overdue"
      checked={overdue}
      onChange={(e) => { setOverdue(e.target.checked); applyFilters(e.target.checked); }}
    />
  }
/>
```

## Typing suggestions

Pass `properties` to turn on a real type-ahead dropdown for the field itself — an ARIA combobox (`role="combobox"` + `role="listbox"`, `aria-activedescendant` for the highlighted option) modeled directly on `<SearchInput>`'s own, not `<DropdownMenu>` (which would move real focus onto a menu item and steal it away from the input mid-type):

```tsx
const properties = [
  {
    key: "status",
    label: "status",
    values: [
      { value: "overdue", label: "Overdue" },
      { value: "paid", label: "Paid" },
    ],
  },
];

<SearchFilter label="Invoices" properties={properties} />
```

Typing a bare word (no colon yet) suggests matching *properties*, shown as `"status:"`. Typing `"status:"` (or `"status:pa"`) narrows the list to that property's own values instead — `key` is matched case-insensitively. Picking a property inserts `"key:"` with no trailing space, so typing continues straight into its values; picking a value inserts `"key:value "` (trailing space), completing that clause. Only the word currently being typed — the last whitespace-delimited run of the field's text — is ever replaced, so earlier finished clauses are left alone.

## The trailing icon is the filter toggle, not a clear button

Confirmed from Figma: the funnel icon swaps to an X only while the panel is open — regardless of whether `value` is empty or filled with a filter summary. It's not `<SearchInput>`'s "clear the typed text" button; clicking it toggles the panel, and clicking it again (or Escape, or an outside click) closes it. There's no separate clear-all — clearing the query is ordinary text editing, the same as any other field.

## Controlling the panel

Useful if something inside `filters` (e.g. an "Apply" button) should also close the panel — control `filtersOpen` the same way you'd control any other open state:

```tsx
const [filtersOpen, setFiltersOpen] = useState(false);

<SearchFilter
  filtersOpen={filtersOpen}
  onFiltersOpenChange={setFiltersOpen}
  filters={
    <>
      ...
      <Button onClick={() => setFiltersOpen(false)}>Apply</Button>
    </>
  }
/>
```

## Accessibility

- The filter button gets `aria-haspopup="menu"` from `<DropdownMenuTrigger>` — not quite accurate (the panel isn't a menu), a known limitation shared with every other `<DropdownMenuPanel>` consumer; see the DropdownMenu docs.
- Opening the panel doesn't move focus anywhere — there's no safe assumption about what inside arbitrary `filters` content should receive it. Escape closes the panel and returns focus to the filter button.
- The suggestions dropdown never moves real focus either — the input keeps it the whole time. The highlighted option is tracked as plain state and exposed via `aria-activedescendant`, with the usual Arrow/Home/End/Enter/Escape keys wired to the input itself.
- Sets `aria-invalid="true"` automatically when `status="error"`.

## The filter panel's width

The panel is at least as wide as the field it's anchored to (never narrower, so it can't clip its own content) but can grow wider when `filters` genuinely needs the room — it's a minimum, not an exact match.
