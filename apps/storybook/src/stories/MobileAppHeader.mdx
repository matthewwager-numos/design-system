# MobileAppHeader

A mobile page header: a branded app icon + title, a row of tabs for switching between that page's sub-views, and an optional trailing action — matches Figma's MobileAppHeader exactly.

<Primary />

<Controls />

## When to use

- The header for a single page/app section in a mobile layout — below `<MobileNav>`'s own top bar, at the top of that page's actual content — when that page has its own set of sub-views to switch between (Figma's example: an "Accruals" page with Recurring/One-time/Templates/Archived).

## Implementation

```tsx
import { MobileAppHeader, Tab } from "@numosai/ui";
import "@numosai/ui/styles.css"; // once, at your app entry

const [tab, setTab] = useState("recurring");

<MobileAppHeader icon="accruals" title="Accruals" value={tab} onValueChange={setTab}>
  <Tab value="recurring">Recurring</Tab>
  <Tab value="one-time">One-time</Tab>
  <Tab value="templates">Templates</Tab>
  <Tab value="archived">Archived</Tab>
</MobileAppHeader>
```

## Nothing here is reimplemented

The icon is a real `<AppIcon>` — confirmed as a scaled-down instance of the same component, not a new one: Figma's own 4.8px corner radius on this header's icon is exactly `<AppIcon>`'s usual 8px radius at the 0.6× scale down from its normal 40px to this header's 24px, not a distinct design decision.

The tabs are the real `<Tabs>`/`<TabList>`/`<Tab>` components — `children` takes `<Tab>`s directly, same as anywhere else `<Tabs>` is used. Confirmed color-for-color identical to their existing styling (unselected `content-brand-primary`, selected `content-base`, the sliding `border-brand` indicator) — nothing about tab appearance is overridden here.

There's deliberately no paired `<TabPanel>` inside this component: the sub-page content these tabs switch between lives in the page below the header, not inside it. Read `value`/`onValueChange` the same way you would with a standalone `<Tabs>`, and render that content yourself alongside `<MobileAppHeader>`:

```tsx
<MobileAppHeader icon="accruals" title="Accruals" value={tab} onValueChange={setTab}>
  <Tab value="recurring">Recurring</Tab>
  <Tab value="one-time">One-time</Tab>
</MobileAppHeader>

{tab === "recurring" && <RecurringAccrualsList />}
{tab === "one-time" && <OneTimeAccrualsList />}
```

## Overflow

Real phone screens can easily have more tabs than fit — the title and the tab row scroll horizontally together, as one strip, rather than wrapping or overflowing the header. Confirmed from Figma: the icon is the only thing that stays fixed, not just the tabs. A separator line between the title and the tabs rides along with that same scroll at first, but it's `position: sticky` — once it reaches the scroll container's own edge (a fixed 8px right of the icon), it anchors there instead of continuing, while the title (ahead of it) keeps scrolling out of view and the tabs (behind it) keep sliding past that same anchored point. A soft edge fade (real scroll position toggling it, not a static overlay) hints there's more to scroll to in whichever direction actually has more.

## Tapping the icon

The icon is a real button: tapping it scrolls the title/tabs strip back to the start (an actual animated `scrollTo`, since there's no single CSS property to transition when what's moving is scroll position) and selects the first `<Tab>` by DOM order. `MobileAppHeader` tracks the selected value itself for this (the same controlled/uncontrolled duality `<Tabs>` has on its own) rather than leaving that state inside the nested `<Tabs>` where it couldn't reach it. Pass `onIconClick` too for anything else that tap should also trigger, or if the tab you actually want selected isn't the first one.

## Props

`icon` (required — any `AppIconName`), `title` (required), `children` (required — `<Tab>`s), `value`, `defaultValue`, `onValueChange`, `onIconClick`, `actions`, `className`.
